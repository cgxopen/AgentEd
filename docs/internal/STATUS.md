## 2. Current state snapshot

- `main`: editor codebase (Tauri 2 + TypeScript + TipTap), version 0.2.0. R-C3 holds on every exit path; R-C2 holds across ten list shapes with one recorded exception; R-C13 is uniform — a bare URL stays text whether pasted, typed or opened from a file; links are created only through explicit UI, with schemes allow-listed on both creation and following.
- **Images, the success side**, settled after four rounds: `assets/` is created by the save flow rather than by an insert (#45); consent is asked once per folder; a document whose images could not be written stays modified; a document just given a destination says once that it is waiting for a save (#48); **identity is content, never name** (#52).
- **Images, the refusal side**, now has a channel: every exit of an insert reports **one outcome** (#61, merged as #63), named in the editor layer and worded in `src/app/image-insert-report.ts`. A cancellation the user made is a different kind from a refusal the application made, and the switch is exhaustive — #51, #46 and #58 each add a kind and cannot compile until someone decides what the user hears.
- **Drag & drop has never worked on the Windows build** (#65). `dragDropEnabled` has never been set in `tauri.conf.json` and Tauri v2 defaults it to `true`, so Tauri replaces WebView2's drag-drop handler and the webview receives no HTML5 `drop` event. One of the three routes R-C5 names — paste / drop / Insert Media — does not exist on the primary target, and has not since the conversion. Not a regression, invisible to every test (it works on the web build), and found only because #63's manual pass tried to use it.
- **A cancelled `assets/` folder disables images for the rest of the document** (#66). R-C5 never promised that; the stickiness came from symmetry with the acceptance, which is right in the code and wrong in the product. Decided: **cancel means "not this image"** — the refusal is not remembered, the agreement still is.
- **R-C14 does not exist in the build.** `saveMarkdown` writes unconditionally — no `mtime`, no hash, no prompt — while REQUIREMENTS, CLAUDE.md and CONTRIBUTING.md all state it as an invariant. Filed as **#55** and blocking for publication.
- Statusbar shows all three counts (R-C12); **About** reports version and build commit (Q5), matching the artifact it was built from.
- CI: `ci.yml` (Linux checks, Windows build, docs-only path gating, `pipeline-ok`, Windows installer as a 7-day PR artifact), `nightly.yml` (Windows-only, activity guard), `release.yml` (`v*` tags, full matrix incl. macOS). Measured installer size: **2.57 MB**, inside Q1. Five known gaps: no timeouts (#47), no cache `restore-keys` (#53), `vite.config.ts` anchored to the working directory (#41), a docs-only merge still running the full build on `main` (#57), and a PR artifact named after the merge commit while WORKFLOW.md says that means it is the wrong build (#64).
- **`CONTRIBUTING.md`, `SECURITY.md`, `LICENSE` and `.github/FUNDING.yml` all exist** — confirmed against the tree on 2026-08-19, having been assumed absent in planning until then.
- **The README is inaccurate in three places** and needs a pass before anyone reads it: the reset note points at issue #5 for a conversion that landed on 2026-08-14 via #7 and #10; *"Coming next"* lists predictable paste, shipped in #21; and Prerequisites ask for Node 22 while CI validates on Node 20.
- Branch protection: `protect-main` — PR-only, squash-only, restrict deletions, block force pushes, head branches auto-deleted, **`Pipeline OK` required** (confirmed against the active ruleset, 2026-08-19; #20 §F had listed this as pending and was stale). Whether the ruleset behaves as intended against a **fork** pull request once the repository is public is a separate, open question — #20 §F.
- Working model: owner (decisions, testing, releases) + AMP (requirements, issues, review, this file) + DEV (Claude Code sessions). No dedicated OPS role — §5, 2026-08-15. English for everything on GitHub.

## 4. Decision debt / open items

- **Multi-tab editing — four questions, none technical, all blocking the issue.**
  1. **Tabs or windows?** R-C8 already promises multiple isolated windows. Tabs are a second model of multiplicity on top of the first: do they coexist, or replace it?
  2. **Is the unsaved-changes gate per tab or global?** Closing a window with three tabs, two modified — one question or two?
  3. **What is a session?** Do tabs reopen on launch? If so, that is the first state AgentEd persists about the user's work, which touches the "no vault, no account" promise directly.
  4. **Does the sidebar follow the active tab**, or stay on the folder that was opened?

## 5. Milestone log (newest first)

- **2026-08-19 — An insert now reports one outcome for every exit (#63, closing #61), and the manual pass found more than the refactor did.** The structural half went as specified and changed nothing the user sees: the contract lives in `src/editor/image-insert-outcome.ts`, the words live in `src/app/image-insert-report.ts`, the silence on a user cancellation is a branch with its reasoning written in it rather than an omission, and the app-layer switch is exhaustive — so #51, #46 and #58 now each fail to compile until someone decides what the user hears.
  DEV's encoding argument is worth keeping: the outcome is **pushed, not returned**, because `void handleImageFile(...)` in the paste and drop plugins is exactly where a returned value dies and the type system has nothing to say about it — and the parameter was made **required**, which turned "should report" into "cannot compile without reporting" and made the compiler list every stale call site. Review added one check the diff could not show: `createEditor`'s image parameters became a required-or-nothing object, so an unwired editor no longer registers the drop plugin at all — a real behaviour change everywhere except that `src/main.ts` is the only production call site and passes the full object.
  **Then the Windows pass earned its place again.** Two findings, neither of them a regression, neither reachable by CI:
  **Drag & drop has never worked on Windows (#65).** `dragDropEnabled` was never set, Tauri v2 defaults it to `true`, and with it enabled Tauri replaces WebView2's drag-drop handler — so no HTML5 `drop` event reaches the webview and the ProseMirror handler cannot fire. One of the three routes R-C5 names has not existed on the primary target since the conversion. It works on the web build, which is precisely why nothing caught it: the test surface and the shipped target disagree, and only a human on Windows could see the difference.
  **A cancelled `assets/` folder disabled images for the rest of the document (#66).** R-C5 never promised that. The stickiness arrived from symmetry with the acceptance — recorded in this log as *"fixed the refusal side the same way"* — and symmetry is the wrong instinct here: remembering a **yes** saves a dialog, remembering a **no** removes a feature, with no way in the interface to change the answer. It was also inconsistent with the Save As cancellation one gesture earlier, which is not remembered at all. Decided: **cancel means "not this image"**. Rejected: keeping the refusal and explaining it, which needs a message teaching the user how to undo an answer and narrates the silence instead of removing it.
  **The reading that connects them**, declared as a reading rather than a measurement: the insert loop fires one `handleImageFile` per file **without awaiting**, and the consent flags are written only after the dialog resolves, so several images in one gesture can each reach the dialog before any answer exists. Invisible today because the only multi-file gesture on Windows is drop, and drop is dead. #65 unmasks it and #66 widens it; recorded on #65 with a criterion — one gesture asks at most once — to be measured rather than argued.
- **2026-08-19 — The silence around a refused image insert, decided as one thing** (#61 opened; #51, #46 and #58 sequenced behind it). Three issues filed from three separate investigations all described an image insert that ends without telling the user anything. Read together in the code, they are not three coincidences. `handleImageFile` has five exits: the success one has had a declared channel since #48 — *"the insert's only success signal"*, named in the editor layer and worded in the app layer — and the four failing ones have none. Two of them invent a message inside the editor layer, and three unrelated causes leave through a single silent `return`: a cancellation the user made, a consent that leaked in from another document (#51), and a capability the web build does not have (#46).
  **What #50 got right on one side was never done on the other.** There, the four "shows nothing" criteria fall out of the structure — every bail-out returns before there is anything to announce. On the failure side nothing falls out of anything, which is why each of the three issues had to decide separately what a refusal says, and why the next branch added after them would start silent by default. **Decided: one outcome per insert**, distinguishing a cancellation the *user* made — which stays silent, because the user already knows what they refused — from a refusal the *application* made, which speaks.
  The two rejected alternatives are worth keeping, because both were cheaper. Fixing the message inside each of the three issues decides the tone of a refusal three times and leaves the next silent branch just as easy to write. A shared message module with the control flow untouched unifies the vocabulary but leaves silence-by-omission intact: a branch that calls nothing still says nothing.
  **Also decided: an unreadable `assets/` folder refuses the insert** rather than proceeding with a name it cannot verify. The alternative — proceed, but never reuse or claim a name — buys the user one image at the price of a third naming regime, living only on a path nobody reaches on purpose and which nobody therefore re-tests after touching the naming code. R-C5 gains its clause in #58's own PR. The distinction that makes the refusal safe is that a folder which does not *exist* yet is the ordinary state of every never-saved document since #45, and must stay silent and successful.
- **2026-08-19 — Identity is content, never name (#56, closing #52).** The same picture inserted twice is stored once and referenced twice; two different pictures that want one name are both kept, the second suffixed. Markdown needed no machinery for this — the reference *is* the path, so the same path twice is already a shared image, and all that was required was a name not to allocate.
  **The risk was never the feature.** A deduplication keyed on names destroys one of two different pictures, silently, and the tests for that row were written before the code. The review traced it through all four routes that reach a file name, and went looking for the one asymmetry that would have been fatal: this change introduces a deliberately case-insensitive name comparison, and had the older collision resolver stayed case-sensitive, Windows would have let `Diagram.png` and `diagram.png` become one file. Both are case-insensitive; they are a pair, and the next person to touch either needs to know it. That case is also **unreachable by CI**, which runs on a case-sensitive filesystem — it was verified by hand on Windows, and the corruption would only have appeared after a close and reopen, since a live document renders from memory.
  DEV also caught a fixture this change would have quietly drained: `assets-dir-deferral.test.ts` built every image from the same eight bytes, so after deduplication its three "different" inserts would have collapsed into one and the test would have kept passing while asserting almost nothing. Nothing in the issue or the brief pointed at it.
- **2026-08-19 — The gate audited against the tree, and three of its statements were wrong.** `CONTRIBUTING.md` already exists — including the item AMP added to #20 that same morning asking for it to be written, added without looking at the repository. `SECURITY.md`, `LICENSE` and `FUNDING.yml` exist too. And this file and #20 §F disagreed about `Pipeline OK`; the owner confirmed against the active ruleset that it is required, so this file was right and the checklist was stale.
  **The finding that matters is #55.** R-C14 — no silent overwrite — is asserted in REQUIREMENTS, in CLAUDE.md's non-negotiable list, and in CONTRIBUTING.md's quality bars, where outside contributors are told a PR violating it will not merge. `saveMarkdown` writes unconditionally. It is the only committed pre-public feature that cannot be deferred by amending REQUIREMENTS §8, because it is not a promise we chose to make but an invariant already declared.
  Counted against the tree, what remains is roughly eleven owner-side settings, eleven single-turn items, and ten multi-turn projects — of which the committed features are about a third. Also recorded: the README is inaccurate in three places today, which matters more than the screenshot work because it is the front page.
- **2026-08-19 — A named destination now says it is not yet a save (#50, closing #48).** The tail of #14, and the debt #45 contracted: before it, choosing a destination for an image produced at least an `assets/` folder, and removing that left the insert flow with no visible feedback at all.
  The implementation is worth noting for its seam rather than its feature. The notification is declared in the editor layer as *the insert's only success signal* and says nothing about what to do with it; the app layer owns the wording and the once-per-document rule. Because it fires after the image lands, every bail-out above it returns before there is anything to announce — so the four "shows nothing" criteria fall out of the structure instead of being four guards that a later edit could get out of step.
  R-C5 gained the clause on the Q5 precedent: the cue exists to pay for a deliberate absence of feedback that R-C5 itself created, so a refactor dropping it should read as a regression rather than quietly restoring the confusion.
- **2026-08-19 — A day of CI trouble, and what it actually taught.** Three separate causes were mistaken for one. A mirror stalled mid-download of a 25 MB package (#45); the same mirror was unreachable and apt absorbed roughly fifteen minutes retrying it before falling back (#50); and one run spent half an hour waiting for a runner before starting at all. **Only the first two are hangs**, and `timeout-minutes` does not cover queue time — so #47 makes a hang visible without making CI feel faster, which is stated in the issue so nobody measures it by wall clock and concludes it failed.
  #47 was reshaped as a result: the ceiling goes on the **step**, not the job, because the Rust job legitimately ranges from 1m42s to 16m41s depending on the cache, and any job ceiling above the slow end is longer than the stall it exists to catch. #53 was opened for the cache itself, and #57 for the observation that a docs-only *merge* still rebuilds everything, because the path filter only runs for pull requests.
  AMP's first reading — *"infrastructure, it clears on a re-run"* — was too generous, and the correction is recorded in the issue rather than quietly edited away.
